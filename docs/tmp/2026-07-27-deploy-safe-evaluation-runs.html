Background

Open Chat Studio lets you build a chatbot and then, crucially, check whether it is any good. You assemble a dataset of messages — real conversation turns, or rows uploaded from a CSV — and you attach a set of evaluators to it: an LLM-as-judge that scores tone, a regex checker, a rule that flags refusals. Press the button and the platform runs every evaluator over every message, producing one result row per (message, evaluator) pair. That whole affair is an evaluation run.

A run is slow. Every message may be replayed through the bot to generate a fresh response, and then each evaluator may call out to an LLM to judge it. A thousand-message dataset with three evaluators is thousands of network round-trips. So it happens in the background, on a fleet of Celery workers, while a progress bar spins in the browser.

Skip if you already know Celery, Redis, and how deploys kill workers

A Django web process should never spend ten minutes calling OpenAI while a user waits. So the work is handed off: the web process writes a small message onto a broker — here, Redis — saying "run task evaluate_thing with these arguments". A separate pool of worker processes pulls messages off that queue and executes them. This is Celery.

Celery gives you three more pieces that matter for this change:

  • Celery beat is a scheduler. It periodically enqueues a named task — "every 30 seconds, run coordinate_evaluation_runs". Think cron, but it puts jobs on the same queue as everything else.
  • A chord is a composite primitive: "run this group of N tasks in parallel, and when the last one finishes, run this callback". Celery implements it by keeping a counter in Redis. Each task that finishes decrements it; whoever hits zero fires the callback.
  • The result backend is a key-value store (also Redis here) where tasks can stash their return value or progress metadata under a task id. The celery_progress library is a thin convention on top of it: the worker writes {current, total, percent} under an id, and a JavaScript poller in the browser reads it back over an endpoint and moves a progress bar.

Now the part that breaks things. When Open Chat Studio deploys, running workers are told to stop. They get a SIGTERM, which asks them politely to finish the current task; if they take too long, they get a SIGKILL, which stops them mid-instruction with no chance to clean up. Any state a worker was holding in memory is gone. And unlike a database row, Redis keys are not the system of record: a chord counter, a progress blob, an unacknowledged queue message — these can be lost, expired, or left in a state nobody will ever look at again.

Two Celery details make crash behaviour tractable, and both show up in this branch. acks_late means the worker acknowledges a queue message only after the task finishes, rather than when it picks it up; if the worker dies mid-task, the broker eventually notices the message was never acked and hands it to somebody else. How long "eventually" is, is the visibility timeout — five minutes in this project's production settings (config/settings_production.py:72). The catch: redelivery means the task runs again from the top, so anything it does must be safe to repeat.

Two other things that were already true

Two pre-existing features of the evaluations app set the stage, and both are documented as their own decisions.

Auto-population (ADR-0019). A dataset can be wired to a source chatbot so that new conversations flow into it automatically. A beat task, auto_populate_eval_datasets, runs every five minutes and appends whatever is new. In other words: a dataset is a moving target. The set of messages in it at 10:00 is not the set at 10:05.

Delta runs (ADR-0020). Because datasets grow, you often want to evaluate only the messages that were appended since the last run, rather than paying to re-judge everything. A delta run therefore carries an explicit list of message ids, stored in a many-to-many field on the run called scoped_messages. The reason it is an explicit list of ids, rather than a filter like "messages created after time T", is precisely that a filter re-resolves against a dataset that has since moved. The id list is a frozen scope. Hold that thought — this branch generalises it.

And one guard rail: while a run is PENDING or PROCESSING, you cannot delete or edit the dataset, evaluators, or config it depends on. Attempting it raises InFlightRunsError and the UI tells you to wait for the run to finish. That is a perfectly reasonable rule, right up until a run can never finish.

How an evaluation run used to work

The old flow was about forty lines, and its shape is worth seeing before we take it apart:

apps/evaluations/tasks.py — before
@shared_task(base=TaskbadgerTask)
def run_evaluation_task(evaluation_run_id):
    evaluation_run.status = EvaluationRunStatus.PROCESSING
    evaluation_run.save(update_fields=["status"])

    if evaluation_run.type == EvaluationRunType.PREVIEW:
        messages = list(config.dataset.messages.all()[:PREVIEW_SAMPLE_SIZE])
    elif evaluation_run.type == EvaluationRunType.DELTA:
        messages = list(evaluation_run.scoped_messages.all())
    else:
        messages = list(config.dataset.messages.all())        # <-- an in-memory list

    concurrency_limit = 10
    chunk_size = math.ceil(len(messages) / concurrency_limit)
    chord_result = chord(
        evaluate_single_message_task.chunks(
            [(evaluation_run_id, evaluator_ids, message.id) for message in messages], chunk_size
        ).group()
    )(mark_evaluation_complete.s(evaluation_run_id))          # <-- the callback

    evaluation_run.job_id = chord_result.parent.id            # <-- the group id, for the progress bar
    evaluation_run.save(update_fields=["job_id"])

One dispatcher task reads the messages, splits them into ten chunks, fans the chunks out to workers, and hangs a callback off the end. Each chunk task loops over its messages, evaluating each one and writing result rows. When the tenth chunk finishes, Redis's chord counter hits zero, mark_evaluation_complete fires, and the run is marked COMPLETED — which triggers aggregate computation and stale-tag reversal.

It is a tidy piece of code and, when nothing goes wrong, it is faster than what replaces it. The callback fires the instant the last chunk lands; there is no polling.

Where it broke

Consider a FULL run over 500 messages. Ten chunks of 50. Nine of them finish. Then a deploy lands and the worker holding chunk #7 is killed after message 23 of 50.

The consequences cascade:

  • The run is PROCESSING forever. The progress bar spins forever.
  • InFlightRunsError now blocks editing the dataset, the evaluators, and the config — permanently. The only fix is a developer opening a shell and changing the row by hand.
  • You cannot even recover by "just re-reading the dataset and finishing the job", because auto-population has been appending to that dataset every five minutes. The dataset you would re-read is no longer the dataset the run was evaluating.
The failure in one sentence

A FULL run's scope existed only in a transient in-memory list and its progress only in a Redis chord counter, so a killed worker left a run that was both unfinishable and unrecoverable — and it took the whole config's editability down with it.

Intuition

The fix is a single change of mind, applied consistently: stop remembering things, and start deriving them.

Nothing about a run should live in a process's memory or in a Redis counter. The plan goes in the database. The progress is computed from the database. And a small, stateless task wakes up every thirty seconds, looks at the database, and asks one question: given what I can see right now, what should happen next? If that task is itself killed mid-thought, it does not matter — thirty seconds later another one asks the same question and gets the same answer.

The grid is the truth

Start with the mental model that makes everything else fall out. A run is a grid: one row per planned message, one column per evaluator. Every cell is a result row that either exists or does not.

Every question the old chord answered with Redis state, you can answer by looking at this grid:

  • How far along are we? Count the fully-filled rows.
  • Are we finished? Are all rows full?
  • What work is left? The rows that are not full.
  • Has this message already been evaluated? Look at its row.

Two conditions have to hold for the grid to be usable as the system of record. First, the rows have to be fixed — you cannot count "how many are left" against a plan that keeps growing. Second, a cell must never be able to hold two rows, or the counting breaks. The branch establishes both.

Freezing the plan

Previously, only DELTA runs recorded their scope; FULL and PREVIEW resolved theirs at dispatch time and threw the list away. Now every run type writes its message ids into scoped_messages at creation, inside the same transaction that creates the run, along with a snapshot of the evaluator ids in a new evaluator_ids array field.

Now put auto-population back in the picture and watch why this matters so much. A FULL run starts at 10:00 over 500 messages. At 10:05 the auto-populator appends 12 more.

Key concept — a decidable finish line

If the coordinator asked "does the dataset have a result for every message?", the answer could be no forever: every five minutes the dataset grows faster than the run can catch up. By reading only the frozen 500 ids, "remaining" is a set that can only shrink. Completion becomes decidable. The 12 new messages are simply not this run's problem; a later run picks them up.

Ticks and waves

With the plan in the database, the dispatcher can be replaced by something much dumber. Two pieces:

Each tick dispatches at most BATCHES_PER_TICK × BATCH_SIZE = 10 × 3 = 30 messages, as ten separate three-message tasks. The set of ids it just sent out is written to the run's in_flight array. That set is a wave.

Here is the part that surprises people, and it is worth getting right: the coordinator will not dispatch a new wave while any message in the current wave is still outstanding. The condition is

in_flight = set(run.in_flight or [])
batch_done = not (in_flight & remaining)

— the current wave is "done" only when its intersection with the still-remaining set is empty. One straggler out of thirty keeps the intersection non-empty, and the tick becomes a no-op: no dispatch, just a progress publish. The wave is a barrier.

Deliberate trade-off

The barrier costs throughput: a wave with one slow LLM call idles the other nine batch slots until it lands. What it buys is a coordination state you can describe in one sentence — "these thirty ids are out; the next wave starts when they are all back" — which is exactly what makes the stall detector below simple and correct. Bounded per-tick queue depth also keeps LLM rate-limit pressure predictable.

A deploy, before and after

Now replay the original disaster. Wave of 30 dispatched as ten batch tasks. A worker is running evaluate_message_batch(42, [104, 105, 106]), has finished 104, and gets SIGKILLed.

Redelivery only works if re-running is harmless, so the branch makes the message-level unit idempotent in two layers, belt and braces:

  1. The skip check. evaluate_message begins by querying which of its evaluator ids already have a result row for this (run, message), and drops them. If none remain it returns immediately — before the expensive bot-generation step.
  2. The unique constraint. unique_result_per_run_message_evaluator on (run, message, evaluator). If two deliveries pass the skip check simultaneously — a genuine race — the second INSERT fails with IntegrityError, which is caught and logged as "the other delivery won". The grid is physically incapable of holding two rows in one cell.
Edge case worth knowing

Suppose a message has two evaluators, the first wrote its row, and the worker died before the second ran. On redelivery, bot generation runs again, producing a fresh bot response — so evaluator #2 judges a different response than evaluator #1 did. The code documents this as an accepted crash-path artifact rather than paying to persist the bot response. It only occurs when a worker dies partway through a single message.

When a message never comes back

Redelivery covers the killed worker. It does not cover every way a wave can go quiet: a task that raised SoftTimeLimitExceeded is acked and gone; a queue can lose a message; an evaluator can wedge. So the coordinator has a second recovery path driven purely by clocks.

A run is stalled if the most recent of these two timestamps is more than STALL_TIMEOUT (12 minutes) old:

  • the created_at of the newest EvaluationResult for the run, and
  • batch_dispatched_at, the moment the current wave was sent.

Taking the later of the two matters in both directions. Without the batch_dispatched_at floor, a wave dispatched thirty seconds ago into a run whose last result landed an hour ago would look instantly stalled. Without the newest-result arm, a legitimately slow wave that has been steadily producing results for fifteen minutes would be re-dispatched underneath itself. Both directions have a test.

When a stall is detected, the coordinator re-dispatches only the unfinished members of the current wave — never new work — and adjusts a counter:

Marking the run FAILED is the point of the whole exercise. FAILED is terminal, so it drops out of NON_TERMINAL_RUN_STATUSES: the coordinator stops driving it, and — the part that actually helps a user — InFlightRunsError stops blocking edits to the dataset, evaluators, and config. The permanently-wedged state that used to need a shell session now resolves itself in thirty-six minutes.

2. Freezing the plan at creation

The run-type branch moved out of the Celery task and into EvaluationConfig.run() (apps/evaluations/models.py:494-532), where it now happens inside a transaction, at creation time:

apps/evaluations/models.py
with transaction.atomic():
    run = EvaluationRun.objects.create(
        team=self.team, config=self, generation_experiment=generation_experiment,
        status=EvaluationRunStatus.PENDING, type=run_type,
        job_id=str(uuid.uuid4()),
        evaluator_ids=list(self.evaluators.values_list("id", flat=True)),
    )

    if run_type == EvaluationRunType.PREVIEW:
        message_ids = list(self.dataset.messages.values_list("id", flat=True)[:PREVIEW_SAMPLE_SIZE])
    elif run_type == EvaluationRunType.DELTA:
        message_ids = [message.id for message in (scoped_messages or [])]
    else:  # FULL
        message_ids = list(self.dataset.messages.values_list("id", flat=True))

    if message_ids:
        run.scoped_messages.add(*message_ids)

Three things changed here beyond the move. The window in which auto-population could shift the plan shrank from "between creation and dispatch" to zero. job_id became a locally generated UUID rather than a Celery group id — more on that in §6. And values_list("id", flat=True) replaced materialising model instances, since only ids are needed.

3. The worker side: dumb batches, idempotent messages

The old evaluate_single_message_task became a plain function, evaluate_message — commit 783e33302, "make evaluate_message a plain function". It is only ever called in-process by the batch task, so being a registered Celery task bought nothing and cost a name that implied it could be dispatched alone.

The function grew one guard at the top (apps/evaluations/tasks.py:188-190):

pending_evaluator_ids = _pending_evaluator_ids(evaluation_run, message_id, evaluator_ids)
if not pending_evaluator_ids:
    return
# ... bot generation and evaluation only run for pending_evaluator_ids

Placed before bot generation, so a redelivered message that is already complete costs one indexed query rather than an LLM round-trip.

The old body's inline try/except tangle was extracted into two helpers. _run_evaluator_on_message holds the "on failure, store {"error": …} and move on" policy; _create_evaluation_result holds the insert and the duplicate-race absorption:

apps/evaluations/tasks.py:111-131
try:
    with transaction.atomic():
        evaluation_result = EvaluationResult.objects.create(...)
        if apply_tags:
            _maybe_apply_tag_rules(evaluation_run, evaluator, evaluation_result, message)
except IntegrityError:

The docstring above this block is unusually careful, and deservedly so: the try deliberately wraps the tag application as well, so result and tags commit together — but that means any IntegrityError from tagging would be misread as "a duplicate won". It argues why that cannot happen today (tag writes use bulk_create(ignore_conflicts=True) against a unique key containing the brand-new result id) and states what to do if it ever could. That is the right way to leave a guard like this behind you.

And the new task, which is deliberately as boring as possible:

apps/evaluations/tasks.py:211-231
@shared_task(acks_late=True, soft_time_limit=BATCH_SOFT_TIME_LIMIT)
def evaluate_message_batch(evaluation_run_id: int, message_ids: list[int]) -> None:
    run = EvaluationRun.objects.get(id=evaluation_run_id)      # (DoesNotExist -> log and drop)

    if run.status != EvaluationRunStatus.PROCESSING:
        logger.info("EvaluationRun %s no longer processing (%s); dropping batch", ...)
        return

    for message_id in message_ids:
        evaluate_message(evaluation_run_id, run.evaluator_ids, message_id)

No refill, no completion check, no rescheduling. The status guard is what stops a batch redelivered after a run was marked FAILED from quietly resurrecting work on a dead run. soft_time_limit = 240s sits deliberately under the 5-minute visibility timeout, so a wedged batch raises inside the worker rather than being redelivered while still running.

4. The coordinator: one tick, four branches

All the intelligence lives in one pure-ish function, _coordinate_locked_run (apps/evaluations/tasks.py:324-358). It is handed an already-locked run, mutates and saves the run's coordination state, and returns a _TickResult describing what the caller should do after the transaction commits. It never dispatches and never publishes.

plan_ids = list(run.scoped_messages.values_list("id", flat=True))
total = len(plan_ids)
evaluator_ids = run.evaluator_ids or []
remaining = set(plan_ids) - _done_message_ids(run, plan_ids, evaluator_ids)
in_flight = set(run.in_flight or [])

5. Locking, dispatch ordering, and the beat

_drive_run is short but every line is load-bearing:

apps/evaluations/tasks.py:361-383
with transaction.atomic():
    run = (
        EvaluationRun.objects.select_for_update(skip_locked=True)
        .filter(id=run_id, status__in=NON_TERMINAL_RUN_STATUSES)
        .first()
    )
    if run is None:
        return  # locked by another driver, or already terminal/gone
    with current_team(run.team):
        result = _coordinate_locked_run(run)

with current_team(run.team):
    for batch in result.batches:
        evaluate_message_batch.delay(run.id, batch)
    _ensure_taskbadger_task(run, result.total)
    _publish_tick(run, result)
  • select_for_update(skip_locked=True) means overlapping sweeps partition the work rather than queueing behind each other. If tick N is still grinding through run 42 when tick N+1 starts, N+1 skips run 42 and moves on. No double dispatch, no lock convoy.
  • Dispatch happens after commit. Coordination state is saved before any .delay(). If the process dies in between, the run has recorded a wave it never actually sent — under-dispatch, which the stall branch repairs in twelve minutes. The reverse order would dispatch work the database has no record of, which nothing repairs.
  • Taskbadger is touched outside the lock. Commit 9476980fc moved task creation after the transaction specifically so a blocking HTTP call never holds a row lock while other runs in the sweep wait — and so a rolled-back tick cannot leave an orphaned remote task pointing at a discarded id.

The sweep itself is deliberately unremarkable: order non-terminal runs by created_at, drive each one, and wrap each in its own try/except so one bad run cannot abort the sweep for everybody else.

The old run_evaluation_task survives, gutted down to a fast path. Its only job now is to skip the up-to-30-second wait for the first beat:

@shared_task
def run_evaluation_task(evaluation_run_id: int) -> None:
    """Fast-path kick for a freshly created run..."""
    try:
        _drive_run(evaluation_run_id)
    except Exception as e:
        logger.exception(...)
        _mark_run_failed(evaluation_run_id, str(e))

If that dispatcher is lost to a deploy, nothing is broken: the run sits in PENDING and the beat's first branch picks it up. mark_evaluation_complete is deleted outright — completion is now derived, not signalled.

Registration, in config/settings.py:

"evaluations.tasks.coordinate_evaluation_runs": {
    "task": "apps.evaluations.tasks.coordinate_evaluation_runs",
    "schedule": 30,
},

plus both new tasks added to Taskbadger's auto-tracking exclusion list — a task that fires 2,880 times a day, and one that fires ten times a wave, would drown the monitoring signal. The run gets exactly one Taskbadger task, created on its first tick and updated on every subsequent one.

6. Progress: a made-up job id and a real progress bar

The old progress bar polled the Celery group status endpoint using the chord's group id, and reported "batches evaluated" — with a slightly baffling current / 100 in the template, an artifact of how group progress was reported. There is no group any more, so the mechanism changes.

The run's job_id is now just a UUID minted at creation. It corresponds to no Celery task at all. The coordinator writes progress metadata directly into the result backend under that key:

apps/evaluations/tasks.py:436-457 — _publish_progress
meta = {
    "pending": False,
    "current": current,
    "total": total,
    "percent": percent,
    "description": f"{current} of {total} evaluated",
}
state = "SUCCESS" if stop else PROGRESS_STATE
current_app.backend.store_result(job_id, meta, state)

The browser polls celery_progress:task_status for that id and cannot tell the difference. Wrapped in a try/except: a failed progress publish must never fail a tick.

A small trick

Both terminal outcomes — success and failure — publish state "SUCCESS". That is not a bug: it is the signal that tells the celery_progress poller to stop polling and reload the page. The reloaded page then renders the run's real status from the database, which may well be FAILED. "SUCCESS" here means "the polling job is over", not "the evaluation went well".

The view change is one line of substance (evaluation_config_views.py:278-280): the context key is renamed group_job_id → celery_job_id, and the progress bar now shows for PENDING runs too, not just PROCESSING — which matters more than it used to, since a run can now sit in PENDING for up to thirty seconds. In exchange, the <meta http-equiv="refresh" content="2"> fallback that hard-reloaded the page every two seconds is gone.

7. Everything else

  • test_evaluation_coordination.py (+543 lines) is the new heart of the test suite: plan freezing per run type, the unique constraint, the three idempotency paths, each of the four tick branches, both arms of the stall clock, the MAX_STALLS escalator, and progress publishing. The one to read first is test_full_run_reaches_completion_over_multiple_ticks — it drives a 35-message run to completion by alternating "tick" and "drain everything that got dispatched", then asserts 35 results and no duplicates. That is the whole design in one test.
  • Existing tests were rewritten where they encoded the old machinery. The delta test that monkeypatched chord and chunks with fake classes now just asserts on evaluate_message_batch.delay arguments; the two mark_evaluation_complete tests became one sweep test. test_run_without_scoped_messages_has_empty_scope was renamed and inverted into test_full_run_freezes_all_dataset_messages — a nice marker of the behaviour change.
  • Type hints were added across the module in two dedicated commits (5af5ae47d, 6c24aadae), which accounts for a good slice of the diff that has nothing to do with coordination.
  • api-schemas/export.yml is regenerated: the five new fields appear in the exported OpenAPI schema, along with the revised scoped_messages help text.
  • ADR-0046 records the decision, marked PROPOSED, extending ADR-0020, wired into docs/adr/index.md and the mkdocs nav. Its "Alternatives considered" section is the useful part: keeping the chord with a watchdog, reading the live dataset for FULL runs, storing the plan as a filter, per-message tasks, and one Taskbadger task per batch — each with the reason it lost.
What you give up

Completion is no longer instant. The chord callback fired the moment the last chunk landed; now completion waits for the next tick, and progress updates have a granularity floor of one beat interval. ADR-0046 accepts this explicitly: for a background job that takes minutes, a few seconds of latency in exchange for surviving a deploy is a trade worth making.
